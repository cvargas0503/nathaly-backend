# F03 — Notificaciones persistentes

Issue #5. `GET /api/v1/notificaciones` y `PATCH /api/v1/notificaciones/:id/leer` requieren sesión y `VER_NOTIFICACIONES`. Aplicar `004_f03_notificaciones.sql` después de 001 y asignar el permiso desde administración de usuarios/permisos. No se aceptan usuarioId/idUsuario para actuar por otra persona.

GET admite page (1 por defecto), limit (20, máximo 100), leida=true/false y tipo (1–30 letras minúsculas/guiones bajos). Respuesta preserva `data`, `noLeidas` y campos `id,tipo,titulo,descripcion,entidad,entidadId,leida,fecha`; agrega pagination. Orden estable fecha/ID descendente. `noLeidas` cuenta todas las alertas activas visibles, sin reducción por página/filtros; pagination.total corresponde a filtros. IDs bigint y entidadId se devuelven como cadenas.

Privadas: UsuarioId=sesión; globales: UsuarioId IS NULL. Lectura se obtiene únicamente de ADMIN.NotificacionLectura, PK notificación/usuario. La migración conserva lecturas privadas previas y no atribuye a nadie el antiguo bit Leida global. PATCH repetido conserva una única fila y su fecha original. Una privada ajena y un ID inexistente responden el mismo 404. Un error de BD responde 500, nunca éxito ficticio.

GET materializa la proyección dentro de una transacción, sin modificar ventas o stock. Stock usa clave `stock-producto-bodega`, condición Stock<=ExistenciaMin y mínimo>0, entidades no eliminadas. Pagos usan `pago-venta` y el código FACT_PENDIENTE que ya consultaba el módulo. Se serializa la reconciliación con sp_getapplock y un índice único filtrado asegura una sola condición activa. Una condición ausente cierra el episodio (Activa=0,FechaCierre UTC). Si reaparece, crea otro ID/fecha inicialmente no leído; el episodio anterior y lecturas se conservan. La fecha de una alerta activa nunca cambia en GET repetidos.

Transición: los nuevos GET entregan IDs persistidos. PATCH acepta `stock-15-2` y `pago-120` si identifican episodio activo. El antiguo `stock-15` devuelve 409 indicando refrescar lista, porque no permite identificar bodega de forma segura. El cliente debe actualizar data antes de reintentar esa lectura; está probado el rechazo explícito. No se devuelve éxito sin efecto.

El endpoint existente `/notificaciones/alertas-stock` mantiene su consulta, bajo el permiso de notificaciones. 400: filtros/ID; 401/403: sesión/permiso; 404: inexistente/ajena; 409: ID heredado ambiguo o lock no adquirido; 500: persistencia. No hay correos, SMS ni jobs.
